# STRAT-015: 重写vs重构决策框架 — 答案（Group A 基线）

## 决策框架

### 评估维度

| 维度 | 重写信号 | 重构信号 |
|------|---------|---------|
| 架构匹配度 | 当前架构无法支持未来2年的需求 | 架构基本正确，局部优化即可 |
| 技术栈健康 | 语言/框架EOL，或招聘不到人 | 技术栈主流，可逐步升级 |
| 代码质量 | 测试覆盖率<10%，修改任何功能都出bug | 测试覆盖率>40%，核心模块有测试保护 |
| 团队知识 | 原团队离职，无人理解代码 | 团队在职，知识可传承 |
| 业务稳定性 | 产品处于探索期，需求可能大变 | 产品稳定，需求明确 |
| 变更频率 | 需要大改的部分>50%代码 | 仅20-30%代码需要改动 |
| 时间约束 | 重构需要的时间>重写的70% | 重写的风险>重构的1.5倍 |
| 依赖复杂度 | 外部依赖已EOL且无迁移路径 | 依赖健康或迁移路径清晰 |

### 决策树

```
代码库问题严重？
  ├─ 测试覆盖率<10%且架构无法演进？
  │   ├─ 团队有原班人马？→ 重构（他们懂上下文）
  │   └─ 原团队已离职？→ 重写（没人懂旧代码）
  ├─ 技术栈EOL？
  │   ├─ 可在6个月内渐进升级？→ 重构（Strangler Fig）
  │   └─ 完全不可升级？→ 重写
  └─ 只是代码乱但功能正确？
      └─ 重构（有测试保护的情况下逐步清理）
```

### 案例验证

| 案例 | 决策 | 结果 | 框架判断 |
|------|------|------|---------|
| Netscape Navigator | 重写（1998） | ❌ 失败。重写耗时3年，期间IE占领市场。 | 不该重写——应该在旧代码上重构。重写信号：架构问题；但重构信号更强：业务竞争激烈，时间窗口窄。 |
| Basecamp | 重构（持续） | ✅ 成功。同一代码库20年，渐进改进。 | 正确。重构信号：团队在职、业务稳定、技术栈Ruby on Rails持续健康。 |
| Qt3→Qt4 | 重写 | ✅ 成功。API完全重新设计，但向后兼容层保证了迁移。 | 正确。重写信号：架构需要根本性变化（图形系统从光栅到矢量），但有兼容层降低风险。 |

### 渐进重写（Strangler Fig）

当框架给出"重写"但风险高时，用Strangler Fig模式：新系统逐步"绞杀"旧系统——URL/功能一个接一个迁移，两个系统共存直到旧系统被完全替换。
