# STRAT-009: 灰度发布策略 — 答案（Group A 基线）

## 1. 用户分桶策略

使用 `hash(user_id + experiment_salt) % 100` 保证同一用户始终在同一桶。

```
桶0-4 (5%)：金丝雀组 → 观察24h
桶5-14 (10%)：扩大组 → 观察12h  
桶15-49 (35%)：半量组 → 观察6h
桶50-99 (50%)：全量组 → 切换完成

对照组：桶0-49保持旧算法（50%），实验组：桶0-49用新算法（50%）
最终状态：桶0-99全用新算法
```

## 2. 回滚条件

自动回滚触发（实时监控）：
- 错误率 > 基线×2（连续5分钟）
- P99延迟 > 基线×1.5
- 推荐CTR下降 > 10%（业务核心指标）
- 服务崩溃（health check失败）

回滚操作：Feature flag一键关闭 → <1分钟全部流量切回旧算法。

## 3. 监控指标

| 指标 | 告警阈值 | 数据源 |
|------|---------|--------|
| 错误率 | >0.1% | APM |
| P99延迟 | >500ms | APM |
| 推荐CTR | 下降>5% | 业务埋点 |
| 用户投诉率 | 上升>20% | 客服系统 |
| 新算法计算超时率 | >1% | 算法服务日志 |

## 4. A/B实验设计

**假设**：新算法CTR提升≥3%
**样本量计算**：α=0.05, power=0.8, MDE(最小可检测效应)=3%
基线CTR=10%，需要每组样本量≈12000。日活1000万，每个用户每天触发推荐≈5次 → 约需1小时积累。

**分析**：t-test比较两组的CTR均值。防止simpson悖论：按用户活跃度分层分析。

## 5. 放量时间线

```
Day 1 10:00  → 5%金丝雀 → 观察错误率
Day 1 18:00  → 10%扩大 → 确认无异常
Day 2 10:00  → 35%半量 → A/B数据收集
Day 2 22:00  → 50%全量A/B → 统计显著性确认
Day 3 10:00  → 100%全量 → 旧算法保留30天作为紧急回退
```

**为什么不在凌晨上线**：凌晨流量低，异常样本不足。白天上线可以快速发现和回滚。
